# Etch v2 specification

Etch v2 is the scope of release **2.0.0**: a Visual Studio Code extension that
previews Europa Universalis IV 1.37.5 interface mods while they are edited, in
the view of the window the game would show and with sample data, and a live
game that reloads each saved file into the game's own window. It replaces 1.x's
game host and diff view (ADR 0005). The milestones before it make no store
release (section 13).

This document says what v2 contains, in what order it is built and what is
left for later. It does not repeat the decisions: they live in the ADRs, in the
live check records and in the resolutions of the
[v2 wayfinder map](https://github.com/happy-dwarf-team/etch/issues/151), which
this document links. Terms are those of [GLOSSARY.md](../../GLOSSARY.md). What
v1 specified and v2 does not change (the offline renderer's drawing, game
text, finding the game and the mods) is in the [v1 specification](v1.md),
whose sections this document names.

**Status: living.** This specification changes by pull request until 2.0.0
and is frozen with it, as v1 was. The open points of the offline renderer stay
in [after-v1.md](after-v1.md); at 2.0.0 that file gives way to an
`after-v2.md` that takes section 16 and the open points of both.

**The trial.** v2 is judged by one trial: editing the province view of
P2KE Patch - Anbennar, and of vanilla, is comfortable and shows well what
changes (section 14).

## 1. Target and principles

- **Game:** EU4 1.37.5, Steam, win64, on Windows only. The live game refuses
  any other `eu4.exe` hash; the offline renderer keeps working on another
  build and warns that results are only checked against 1.37.5.
- **One preview, one renderer.** The preview is drawn by the offline renderer
  alone; the backend switch and the diff view are gone (ADR 0005). It follows
  the unsaved buffer on every keystroke, as in v1.
- **The preview shows a view.** With a window profile the preview draws one
  view of the window, with sample data in its code-filled widgets. Without a
  profile it draws every widget and no sample data, as 1.x did.
- **The live game is the game itself.** Etch starts its private copy of the
  game with the edited mod's playset, the user plays it, and each **saved** file
  is reloaded into the game's own window, with its real data. It is not a
  backend of the preview: the preview learns from it only through pick mode and
  live snapshots.
- **No emulator.** Etch never computes values the way the engine does (income,
  modifier totals) and never evaluates a scripted trigger; values come from a
  save, the files, the live game or are generated.
- **No language server.** Etch reads what it needs itself; it may take ideas
  from CWTools' rules.
- **The player's files are read only.** Etch never writes to the player's game
  folder, profile, saves or mods. It writes into the edited mod's project only
  on the user's request: **Save as view** (`.etch/profiles/`) and
  **Override in my mod** (section 7).
- **Speed first:** the gated budgets of section 9 are requirements.
- **Precision is measured, not claimed:** the precision corpus of ADR 0002,
  now with the province view and the Anbennar playset gating (section 10).
- **No telemetry.** Etch sends nothing anywhere; the game's `CrashReporter.exe`
  is closed after its identity is checked, as in v1.

## 2. Editor features

### Preview and previewed window

As v1 section 2, except:

- The **previewed window** is the top-level window under the cursor, or the
  pinned one. A pick in the live game also pins it (section 7).
- The preview toolbar has `View ▾` and `Data ▾` (sections 4 and 5) and a
  button that starts the live game. The backend switch and **Diff** are gone.
- When the previewed window's profile has a **link** that holds (an
  uncolonised province opens `colonisationpanel` instead of the province view),
  the preview shows a note with a button that pins the linked window.

### Widget outline and navigation

As v1 section 2, with the view drawn in (etch#159):

- Windows of an exclusive group (tab, side panel, the eight sub-panels of
  `province_window`, own or foreign, Anbennar's `aPUI_*`) show as radios under
  a "(one of)" header; every other nested window has an eye.
- An opened window lists its single elements (icons, texts, buttons), each with
  its own eye; a text shows its sample value and the layer it comes from.
- A hand toggle (an eye or a radio set by hand) is marked, counted in the View
  label ("Own province · 1 by hand") and reset from `View ▾`.
- A variant the game does not create at the preview's screen height (a `_large`
  window below 814 px) is struck through.
- Navigation both ways and hover work on what the view draws.

### Commands

- Open the preview; pin or release the previewed window; choose the preview
  resolution (as in v1).
- **Etch: Start the Live Game**, **Etch: Stop the Live Game**,
  **Etch: Remove the Private Install** and a command that opens the live game's
  saves folder (section 6).
- **Etch: Toggle Pick Mode** and **Etch: Override in My Mod** (section 7).
- **Etch: Snapshot from the Live Game** (section 7).

### Settings

The settings of v1 (`etch.gamePath`, `etch.playset`, `etch.language`,
`etch.previewResolution`) stay, plus `etch.liveGame.pickModeKey`, the pick
mode hotkey, default `Ctrl+Shift+E` (section 7).

### Finding the game and the mods

As v1 section 2. The playset decides the window profile layers too
(section 4).

## 3. Offline renderer

As v1 section 3, which keeps the widget kinds, sprites, shaders, textures,
text and layout rules, with these changes:

- **One view.** With a profile, the renderer draws the widgets the view shows:
  a window the view hides is not drawn, nor laid out for hover and navigation.
- **Not created.** Of each `_large` pair the game creates only one: at a screen
  height below 814 px the small variants, above it the `_large` ones
  (etch#155). Drawing both, as 1.x did, is wrong.
- **Code moves.** A `positionType` move the game's code makes (such as
  `top_section_window` to `top_section_position_big` above 813 px) is applied.
- Etch derives the `_large` pairs and the `positionType` moves itself for a
  window that has a profile, so a profile need not write them (ADR 0006).
- **Code-filled content** shows sample data where the profile names a content
  source (section 5): texts, values, list entries from repeaters, frames from
  `frame` rules. Without a source it stays as the `.gui` defines it (v1).
- `if_resolution` is evaluated against the preview resolution, as in v1; the
  resolution selector of a profile takes the same value.

## 4. Views and window profiles

Format and checks: [ADR 0006](../adr/0006-window-profiles-as-layered-jsonc-files.md).
How a mod author writes one: `docs/window-profiles.md`, written in M6 and
linked from the store README.

### Window profiles

- One JSONC file per top-level window and source, checked by a JSON Schema the
  VSIX ships and binds to `.etch/profiles/*.jsonc`. Each file starts with
  `formatVersion: 1`.
- It holds selectors (kinds `resolution`, `data`, `ui`, `scripted`),
  exclusive groups (with an optional `none`), rules (`when` some selectors have
  some values, then `show`, `hide`, `notCreated`, `position` or `frame`),
  named views with a `defaultView`, links, content sources and repeaters
  (section 5). Widgets are addressed by their path of names, with `*` and `**`.
- A `data` selector reads one named fact Etch implements, such as
  `province.ownedByPlayer` or `province.hasGreatProjects`. A new fact needs an
  Etch release.
- **Layers:** vanilla, then each mod of the playset in playset order (by
  Workshop `remote_file_id`, else the descriptor's name), then the mod
  project's `.etch/profiles/<window>.jsonc`. A later layer replaces a whole
  entry by its key, adds one, or removes one with `null`.
- **Checked on load** against the schema and the playset's files: a path
  missing from the window, an unknown selector or value, or a `save` source
  outside the known facts and paths is an error. For the mod project's file it
  goes to Problems with its line; for Etch's own profiles to the log and one
  notice. The faulty entry is skipped and the rest applies.
- A profile records the mod version it was checked with; another version gives
  a notice and the profile still applies. A file with a newer `formatVersion`
  is skipped with a notice.
- **Profiles Etch ships** (`profiles/<source>/` in the repository and the
  VSIX): vanilla and Anbennar, for `provinceview` and for the windows of the
  precision corpus (section 11). A profile for another mod comes by pull
  request; unless its mod is in the corpus it is checked on load only, and the
  documentation says so.

### `View ▾`

As chosen in etch#159 (variant D):

- the ready views of the profile;
- the user's own views: **Save as view** writes the current selectors and hand
  toggles under a name into the mod project's `.etch/profiles/<window>.jsonc`,
  as an ordinary view of the top layer that can be committed;
- every selector, compact, with the source of its value: `auto`
  (resolution), `save`, `live` (section 7), `you` (by hand or a view),
  `default`. A data selector follows the save until the user pins it, and
  "follow save" releases it. The menu stays open while the user clicks;
- after a pick or a snapshot, the note "profile differs in N paths" with
  **Open profile** and **Save as view** (section 7).

## 5. Sample data and saves

### Layers

`Data ▾` shows the stack, upper layers winning, each with how many texts it
fills (etch#159):

1. **Live snapshot** (section 7), a toggle at the top, as of its time.
2. **Save:** a country (the player's first, then any) and a province (any, own
   or foreign) of a chosen save.
3. **Game and mod files** (always on): localisation, names, icons.
4. **Generated:** text of a chosen length (short, typical, long, overflow;
   `typical` by default), numbers, percentages and dates.

Without a profile the preview stays the empty skeleton of v1. The profile picks
no save, country or province; they are the user's choice.

### Content sources and repeaters

- Each code-filled widget path of a profile has a source: `save` (a save path
  such as `provinces.{province}.base_tax`, with a format: number, percent,
  localised), `loc` (a localisation key), `engine` (filled only by a live
  snapshot) or `generated` (text, number, percent or date). The only
  transforms are `sum` and `localise`.
- A **repeater** names an entry template, the save collection the entries come
  from and each entry's field sources; without a save it shows N generated
  entries, N a profile default.
- A value the save lacks (anything the engine works out) falls through to the
  lower layers; Etch never computes it.

### Saves

- **Read:** text saves only, zipped (`meta`/`gamestate`/`ai` with `EU4txt`) or
  plain (autosaves with `compress_autosave=no`). An `EU4bin` save (ironman) is
  detected and named as not readable; no token table can lawfully be shipped.
- **Where from:** any save file the user picks; the quick pick offers the
  player's `save games/` (read only) and the live game's private saves.
- **How:** Etch's own TypeScript reader, never a whole tree (3.3–3.6 s and
  2.2 GB for an Anbennar save): inflate with `node:zlib`, one byte pass that
  indexes every country and province block, then decode (`windows-1252`
  through `TextDecoder`) and parse only the blocks a view needs. The save
  tokenizer accepts `\"` escapes and strings over several lines. `jomini`,
  eu4save, pdx-tools and native tools are not used (etch#154).
- The index is built off the cold-open path: the preview paints from the other
  layers first and takes the save's values when the index is ready.

## 6. Live game

Decided in etch#157 and corrected by the live checks
([docs/live-game-checks.md](../live-game-checks.md)). How it works is in
[docs/live-game.md](../live-game.md) (M8). Of
[docs/game-host.md](../game-host.md), the record of 1.x, these sections still
hold: Layout (without `overlay/`), Before every start, Removal, What the
install never does, The process (without the stop after 30 minutes and the
behind-VS-Code step), Diagnostics from the game (the `error.log` reading),
Texture reload, Mod files over the base game, Restart and watchdog (the
watchdog), and Dialogs (the dialog class).

### Private install and plugins

- The private install is 1.x's game host install, renamed: the junction copy
  in the extension's global storage with the pinned `eu4.exe` hash, created
  after one confirmation, and removed by **Etch: Remove the Private Install**
  (never following a junction). A 1.x install is removed on 2.0.0's first
  activation through the same removal, with one notice.
- It holds the pinned builds of Anvil, `anvil-game`, Bellows, Tongs and Etch's
  plugin (ADR 0004), hashes checked before every start; nothing else loads from
  `anvil/plugins/`. There is no overlay mod.
- **Tongs** is loaded with `enabled = false`: no pipe, hooks or input, only the
  in-process service `tongs.ui` version 1. Etch's plugin declares a hard
  dependency on `tongs` (from 0.17, which gives each widget's
  `definition_file`; pick mode needs the release with `definition_line`,
  [tongs#86](https://github.com/happy-dwarf-team/tongs/issues/86)), which puts
  it in Anvil's main phase, and reads the widget tree only through it: pick
  mode, the stale-root check and the leak count. Tongs is not a user-facing
  tool here.
- **Bellows'** negative file cache may stay on for the playset's mod folders:
  it stops at the game's readiness, and nothing seen after the start depends on
  it (H9).
- The private profile holds descriptors with absolute paths to the playset's
  mods, all owned DLC enabled, and saves of its own.

### Start and stop

- Started only on request: **Etch: Start the Live Game** or the preview's
  button. No idle timeout. One live game per machine, with v1's lock and
  identity checks.
- The first start asks for its own confirmation: the game runs in the
  foreground, takes the player's settings, copies their saves, and counts as
  the player's EU4 session for Steam (Steam refuses to start the player's own
  game beside it and shows them playing, H11).
- Etch does not start the live game while the player's own `eu4.exe` runs,
  and says why. While the live game runs, Etch offers **Etch: Stop the Live
  Game** to a player who wants their own game.
- At every start `settings.txt` and `pdx_settings.txt` are copied from the
  player: resolution, graphics, sound, window mode, UI scale and language as
  they are; changes in the live game do not persist. If the player's autosave
  is off the copy autosaves monthly, and the first start says so.
- A quick pick offers **Continue** (the newest private save), **Main menu**,
  then the player's saves, newest first. A chosen player save is copied into
  the private `save games/` and the game starts with `-continue=<copy>`.
  Ironman saves show greyed out ("reload does not work in ironman") and are not
  copied. A command opens the private saves folder.
- **Stop:** **Etch: Stop the Live Game** or closing the VS Code window, both
  saving first. The game is a child process, so it ends with a crashed VS Code;
  the next start offers the newest save. A quit from the game (reported by the
  plugin, or exit code 0 without a hang) is a stop, not a crash.
- **Exit to Main Menu** in the game ends in a process that starts itself again
  as a child with the same command line (H6); the live game adopts it after
  the identity checks, or closes it, and never counts it as a crash or a second
  game.
- Multiplayer is not blocked; there every reload answers "reload is not
  available in multiplayer". Etch never bypasses the console's refusal in
  ironman and multiplayer.

### Reload policy

On each saved file of the playset, the extension decides and the plugin runs
one job on the main thread (the console dispatcher, as in 1.x):

| Saved file | What the live game does |
| --- | --- |
| A file with a listener whose windows are rebuilt: `provinceview.gui`, the country view's tabs, the ledger, settings, the event window, the HUD files of the in-game idler | `reload <file>`. A rebuild that opens a closed `provinceview` (H2) is followed by an Escape through the game's SDL queue, undone when it opened the game's menu instead |
| `speed_controls.gui` | `reload`, then `reload topbar.gui`, which rebuilds it and counts as a HUD rebuild (H6) |
| `countryview.gui` | planned restart (no listener, and a save load in the same process does not rebuild it, H6) |
| A file whose on-demand window is open (`DeclareWarDialog`) | the plugin closes the window through the game, reloads, and Etch asks the player to reopen it |
| `.gfx`, fonts, `common/custom_gui`, `scripted_guis`, `core.gui` (its templates build windows nothing rebuilds), a file with a top-level name written twice (Anbennar's `countryreformview.gui`) | planned restart, with the reason |
| Localisation | `reloadloc`, then `reload` of the listened panels whose windows are on screen and of one HUD file when the HUD is |
| A texture | `reloadtexture` with every spelling the `.gfx` files use; "Reload failed" for a texture no window holds is not an error |
| A texture a sprite type names that was missing when the game first drew it | planned restart, with that reason (H9) |
| A file whose winning copy in the playset belongs to another mod | nothing is reloaded; Etch names the mod that wins (`game-original-differs`) |

- A `.gui` file created after the start is seen by its `reload` (H9), so a
  file **Override in my mod** creates reloads like any other.
- Etch never sends `reload guianim` (it crashed the game), `reload texture`
  (a 1.3 s freeze) or `reload assets` (not checked) (H10).
- **Stale-root check** after every reload: the plugin collects the root
  widgets built from the file's top-level definitions before the reload and
  compares them by widget id with those alive after it; a liveness read of the
  definitions is not trusted (H3). Hidden stale rows do not hold reloads; a
  visible stale window holds further reloads until a restart.
- **Leaks:** HUD rebuilds leak; after 10 (the tested range) a planned restart
  is asked for. Panel rebuilds leak about 0.6 MB each and are counted; 20 is
  their tested range and sets no limit yet.
- **`error.log`:** new lines go to Problems on the edited file's lines;
  repeats are collapsed (a missing texture writes about 220 lines a second),
  and the binding lines the game writes on every vanilla `provinceview` reload
  (`Missing Button 'close_button'`, `Missing Icon 'remove_parliament'`) are not
  the user's.

### Planned restart and crashes

- A **planned restart** has a cause from the table above, the leak limit or a
  visible stale window. Etch shows "Restart needed: <reason>" with **Restart
  now** and **Later**; until then the live game is marked stale and reloads
  wait. Etch never restarts a played game without the player's click, except
  after a crash.
- It saves through the plugin (the game's `autosave`, `autosave.eu4` in the
  private profile; the console's `savegame` writes nothing), starts again with
  `-continue`, and reopens the recorded view. In the Anbennar playset it
  answers the achievements prompt (Enter on `DefaultConfirm/AgreeButton`) and
  leaves the save's events to the player (H7). VS Code shows its progress;
  there is no time target.
- A **crash** is a dead process, a hang (10 s without a frame or a ping, not
  counted while the game saves or loads), a console fault, or a start that
  ends or hangs. The game restarts at the newest private save (autosave,
  manual or planned-restart save).
- After any restart Etch reopens, best effort, the province of the province
  view (through the game's selection function `0x139C830`, H8) and the open
  country view tab; if that fails the game stays on the map and Etch says so.
- The third crash within 5 minutes stops the live game and names the last
  cause and the last file, as in v1.

### Plugin protocol

The session pipe keeps `hello` and `ping` and goes to protocol version 2 with
the live game's first request; the `job` request and the frame capture are
gone (ADR 0005). It becomes two-way: the plugin pushes picks (section 7).
[docs/plugin-protocol.md](../plugin-protocol.md) records the requests as they
are built.

## 7. Pick mode and live snapshot

### Pick mode

Decided in etch#158 and corrected by the live checks
([docs/pick-mode-checks.md](../pick-mode-checks.md)).

- **Hotkey:** `Ctrl+Shift+E` by default (`etch.liveGame.pickModeKey`, written
  to the plugin's Anvil key setting and taken without a restart), caught in
  the plugin's subclass of the game window's procedure and swallowed; the game
  binds nothing to it. **Etch: Toggle Pick Mode** turns it on or off too and
  brings the game forward. Esc is never touched.
- **Outline and label,** drawn in the plugin's `Present` hook: the hovered
  widget outlined, its top-level window dashed; a label with name, kind, size,
  `<mod> › interface/<file>.gui:<line>` and the shortened path; a badge
  "Etch pick — <key> to leave". Over the map, a tooltip or the console the game
  reports no widget, and the label says "not a GUI widget". A stale widget is
  outlined red and named from its holder, never through its freed definition.
- **The stack under the cursor:** the wheel steps through the visible widgets
  under the pointer, which is how a button's own text is reached (the button is
  the hovered widget, H5): the hovered widget's own widgets and its parents
  first, then any other (a map icon under the window). Top-level windows that
  cover the whole screen (`menubar`, `floating_buttons`) are left out of it.
- **Reads** through `tongs.ui` on the main thread: the hovered widget every
  frame without paths (median 0.08 ms in the probe, 0.28–0.43 ms with Etch's
  plugin), the chain with paths from the visible tree once per click on the
  next frame (11–37 ms, H7).
- **Swallowing the click:** in pick mode the plugin drops every mouse button
  message (down, up, double click, all buttons) and the wheel, **clears the
  `MK_*` bits of every mouse message it passes on** (SDL 2.0.4 rebuilds clicks
  from them, H6) and makes the key-state imports read the buttons as up. Hover
  and tooltips keep working; the keyboard other than the hotkey goes to the
  game. The click that activates the game's window only brings it forward: the
  game reads the pointer only while it is in front.
- **What a click opens:** the definition the game reports: its game path and
  line, the 1-based line of the `{` that opens the widget's block (H2),
  resolved to the playset's winning file. The extension accepts a widget whose
  opening brace is on that line and walks names when the file changed since
  the last reload. Templates (rows built by name, `core.gui` scroll bar parts,
  icon templates from another file) open the referencing widget first, with
  "Go to template"; icons offer "Go to sprite" through Etch's `.gfx` index (the
  game has no file or line for sprites). A stale widget opens by name without a
  line. A click with no widget under it opens nothing.
- After a pick the plugin calls `AllowSetForegroundWindow`, brings VS Code's
  window forward itself (the game is the foreground process at the click; the
  extension tells it VS Code's process and title) and pushes the pick over the
  pipe; VS Code comes forward with the file open, and pick mode **stays on**.
- **Files outside the edited mod** (vanilla, another mod) open read-only with
  "Defined in <mod>, read-only · Override in my mod".
- **Override in my mod** (also **Etch: Override in My Mod** on any interface
  file that is not the mod's): copies the whole winning file byte for byte to
  the same game path in the edited mod's folder and opens the copy at the same
  line. It warns, and still copies, when a later mod of the playset has the
  same file; if the mod already has it, nothing is copied.
- **The preview takes over:** a pick pins the preview on the enclosing
  top-level window, with the selectors the profile recognises set to `live`,
  what it does not know as hand toggles marked "from the game", and a live
  snapshot as of the click. A pick is a moment: the preview does not follow the
  game afterwards.

### Live snapshot

Decided in etch#170.

- **Holds** every widget of the picked top-level window, hidden ones too:
  path, type, `visible`, `enabled`, `checked`, text and rectangle, with list
  rows by position (`…/listbox/row[2]`): the fields of `tongs.ui` version 1,
  read in one `find` of the window's subtree (13–16 ms for the province view;
  the whole tree with hidden widgets took 150–215 ms). Not in v2: code-set
  sprites and frames, text colours, tooltips.
- **Format:** JSON with `formatVersion: 1`, the time taken, the save's name,
  the hash of the window's winning `.gui` file and, once `anvil-game` offers
  it, the game date. Stale widgets are left out and counted; no snapshot is
  taken of a stale top-level window.
- **Taken** by a pick, by **Etch: Snapshot from the Live Game**, or by
  **Refresh from live game** in `Data ▾`, of the previewed window when the game
  has it open.
- **Kept** in the extension's workspace storage, the latest per top-level
  window and playset; never in the mod's project, never shared or exported.
- **Matched** by widget path, list rows by position; values that no longer
  match fall through and `Data ▾` counts them. It never expires by time; after
  a restart or another save it is marked "older"; it is dropped when the
  playset changes or its window no longer exists.
- **Selectors from the snapshot (`live`):** resolution from the game window's
  size; each `data`, `ui` and `scripted` selector gets the value whose rules
  predict exactly the visibility the snapshot shows (the default when several
  fit, "unknown" when none does). Etch reads no facts from the game.
- **Against the profile:** the paths where the profile's prediction differs
  show as hand toggles and as "profile differs in N paths" in `View ▾`. Etch
  writes no rules itself, and the differences are not Problems.

## 8. Resolutions and UI scale

- **Preview:** as v1 section 6: the six corpus resolutions, the monitor's
  native one or a custom size, default from the player's `settings.txt`.
  2560×1440, 3840×2160 and zoom are separate issues
  ([etch#163](https://github.com/happy-dwarf-team/etch/issues/163),
  [etch#162](https://github.com/happy-dwarf-team/etch/issues/162)).
- **Live game:** the player's resolution and window mode, from their copied
  settings; a pick carries the game window's size to the preview's
  `resolution` selector.
- **UI scale:** the preview lays out at 1.0 only, with v1's information
  diagnostic. The live game runs at the player's UI scale.

## 9. Budgets

Measured on the maintainer's machine, not timed in CI (ADR 0004).
[docs/budgets.md](../budgets.md) records the method and every result.

### Gated: the preview

| Budget | Vanilla | Anbennar playset |
| --- | --- | --- |
| Cold open, with the profile and the files layer applied | ≤ 1 s | ≤ 2 s |
| Warm reload (p95), with the profile and sample data applied | ≤ 50 ms | ≤ 50 ms |
| Choosing a save, to the paint with its values | ≤ 1 s | ≤ 2 s |
| Choosing another country or province in `Data ▾`, to the paint (p95) | ≤ 100 ms | ≤ 100 ms |

- The save is never on the cold-open path (section 5).
- The save budgets are measured on the vanilla corpus save (62 MB of text)
  and an Anbennar save of about 112 MB of text, the largest of etch#154, where
  inflating and indexing took about 1 s and a view's blocks about 50 ms.
- Warm reloads and cold opens are measured as in v1, with `provinceview` added
  to the measured windows of both playsets, in its profile's default view.

### Reported: the live game and pick mode

The live game's timing depends on the game's frame rate, so it is reported each
release, not gated, as 1.x's game host was. Targets, measured with Etch's
plugin from the save in VS Code to the changed frame:

| Measure | Target |
| --- | --- |
| A listened file's reload (`provinceview.gui`), p95 | ≤ 150 ms |
| A HUD file's reload (`topbar.gui`), p95 | ≤ 250 ms |
| A pick, from the click to the line in the editor | ≤ 1 s (M9: 32–133 ms) |
| A planned restart, a restart after a crash | no target; progress shown |

For scale: the console call alone took 59 ms at the median and 119 ms at p95
for vanilla `provinceview.gui`, 29/66 ms for Anbennar's and 57/109 ms for
`topbar.gui` (live checks); a pick through `code -g` reached VS Code in
493–656 ms (pick mode checks), and through the pipe with the game bringing
VS Code forward 32–133 ms (M9). A restart to a loaded game took 18–20 s in
vanilla and about 100 s in the Anbennar playset, its achievements prompt
included.

## 10. Playsets and mods v2 must handle

| Playset | Precision (ADR 0002) | Functional requirement |
| --- | --- | --- |
| Vanilla, no mods | gates 2.0.0 | every window of section 11; the live game reloads `provinceview.gui` |
| Vanilla + Proper 2K UI Enhanced | gates 2.0.0 | every window of section 11 |
| Anbennar + Proper 2K UI Enhanced + P2KE Patch - Anbennar | **gates 2.0.0** (reported in v1) | every window the mods override opens in the offline renderer without a crash, with diagnostics; the live game loads its save and reloads the patch's `provinceview.gui` |

- **Anbennar gating:** the playset gates every corpus view that has a working
  recipe in it, at the six corpus resolutions. A view without one (such as
  `diplomacy-dialog`, if the save has no row to click, and `event`) leaves the
  gate only with the maintainer's consent, as the event window did in v1.
- The gate holds for the pinned mod hashes of the manifest: a Workshop update
  of a mod blocks no release, and pinning a new version is a pull request of
  its own with new captures.
- Fixes to the offline renderer that the Anbennar `provinceview` captures call
  for (judged wrong while trying the views prototype, etch#159) are part of M10.
- Window profiles: vanilla's for every playset, Anbennar's added for the
  Anbennar playset (`remote_file_id` 1385440355). Profiles for other big mods
  come later (section 16).

## 11. Windows v2 must handle

- **Any top-level window** previews in the offline renderer; without a profile
  it shows every widget, as in v1.
- **`provinceview`** in vanilla and in the Anbennar playset: a profile with the
  five selectors of etch#155 (screen height, own or foreign, province or state
  tab, the player's side panel and sub-panels, province data such as great
  projects and native buildings), Anbennar's scripted selectors (the province
  button bar and its exclusive `aPUI_*` windows, hand-written), the link to
  `colonisationpanel`, content sources for its code-filled widgets and
  repeaters for its rows.
- **The corpus windows** (v1 section 9): a profile in vanilla and in the
  Anbennar playset with at least the selectors and rules their corpus views
  need to pass the visibility gate, and content sources for the widgets the
  manifest lists as code-filled.
- **The corpus** adds two province views to the manifest, each captured in the
  three playsets at the six resolutions (the two smallest give the small
  variants):
  - `province`: an own province, province tab;
  - `province-foreign`: a foreign province.
- A view may have a **recipe per playset**: the Anbennar playset's save
  (Verne, 11 November 1444) has no ship in construction, and three events it
  opens with cover the middle of the screen (one too tall for its option to be
  clicked at 1080 pixels), so its province views open through the Goto box (a
  province by name) and a click on a map point beside the events, given in
  client heights from the centre so that it is the same province at every size;
  its declare war dialog opens from its one diplomacy row. Windows a playset's
  save shows over every view (those events) are read with each view and masked
  as code-filled (`covers`, corpus/README.md).
- Each capture of a profiled window records its view's selector values in the
  manifest (ADR 0006).
- Not captured in v2: the state tab (`state_window`), `colonisationpanel`, the
  Anbennar province button bar and `aPUI_*` windows (they need country flags,
  which a recipe cannot set without game calls). Their profile entries are
  checked on load only.
- **The live game** handles the files of the reload policy (section 6); every
  other file of the playset takes a planned restart or names its reason.

## 12. Diagnostics

All come from the extension's model unless marked as coming from the live
game. v1's diagnostics of the extension's model stay (v1 section 10); the game
host's (top-level kind it cannot open, a dialog's `shieldtype`, the FPS counter
corner) go. Severities not given are set in implementation.

| Diagnostic | Source |
| --- | --- |
| A window profile entry that fails its check: a missing path, an unknown selector or value, an unknown save source (Error in Problems for the mod project's file; log and one notice for Etch's own) | ADR 0006 |
| A profile with a newer `formatVersion` (skipped), or checked with another mod version (notice) | ADR 0006 |
| A save Etch cannot read (`EU4bin`, ironman), named as such | etch#154 |
| New `error.log` lines, repeats collapsed, the game's own binding lines left out (live game) | section 6 |
| The saved file does not win in the playset: another mod's copy is used (live game: nothing reloaded) | ADR 0005, etch#16 |
| Restart needed, with its reason (notice with **Restart now** and **Later**) | etch#157 |
| A visible stale window holds reloads until a restart (live game) | etch#157, H3 |
| Reload not available in multiplayer or ironman (live game) | etch#152 |
| Live game stopped after 3 crashes in 5 minutes, with the last cause and file | etch#157 |
| Override in my mod: a later mod has the same file, so the copy would not be used (warning before copying) | etch#158 |

The snapshot's "N values no longer match" and "profile differs in N paths"
show in `Data ▾` and `View ▾`, not in Problems.

## 13. Milestones and build order

Version numbers are not given: **no store release comes from `main` between
1.0.x and 2.0.0**. Each milestone ends with the VSIX of the `windows` CI job;
the release-please pull request waits, and 2.0.0 is released with
`Release-As: 2.0.0`. Fixes for 1.0.x (bugs only) are released from
`release/1.x` until 2.0.0, none after (ADR 0005).

After M5, M6–M7 (the preview: `core`, `renderer`, the extension's preview) and
M8 (the plugin and the live game's process) can be built in parallel. M9 needs
M6 and M8. M10's recipes and captures start once M6 lets a capture record its
view's selector values, and finish with 2.0.0.

1. **M5 Retire the game host.** Cut `release/1.x` at `v1.0.1`. Remove from
   `main` what ADR 0005 and etch#156 list: the backend switch, the diff view,
   jobs, preview copies, the backdrop, the overlay mod, the plugin's `job` and
   capture, their diagnostics and checks. Rename the install to the private
   install, its commands to section 2's, and remove a 1.x install on first
   activation with one notice. `docs/game-host.md` becomes "The game host
   (Etch 1.x)", the record of 1.x; the glossary already has its 1.x section.
2. **M6 Views and profiles.** The profile reader with its schema, layers and
   load checks; facts, selectors, groups, rules and views; the `_large` pairs
   and `positionType` moves; `View ▾` and the Widget Outline's radios, eyes and
   hand toggles; **Save as view**; Etch's profiles for `provinceview` and the
   corpus windows, vanilla and Anbennar; `docs/window-profiles.md`.
3. **M7 Sample data and saves.** The save reader (detect, inflate, index,
   blocks); the layers and `Data ▾`; content sources, repeaters and links; the
   save budgets.
4. **M8 Live game.** The private install with Tongs as a pinned build; start
   and stop with the player's settings and saves; protocol 2; the reload policy
   with the stale-root check and leak counts; `error.log`; planned restarts,
   crash recovery and reopening the view; `docs/live-game.md`.
5. **M9 Pick mode and live snapshot.** The hotkey, outline, label and stack in
   the plugin; the push over the pipe; opening the definition, templates and
   sprites; read-only files and **Override in my mod**; the live snapshot, its
   storage and `live` selector values; the comparison with the profile.
6. **M10 Corpus v2 → 2.0.0.** Recipes per playset; the `province` and
   `province-foreign` views in three playsets; selector values in captures and
   the visibility gate; the Anbennar playset to `gate: release`; the renderer
   fixes its captures call for; the budgets of section 9; the live checks still
   open (section 17); the trial; then 2.0.0 by the criteria of section 14.

## 14. Release criteria for 2.0.0

- **Precision:** the gate of ADR 0002 for the three playsets of section 10 at
  every corpus resolution, the province views included. A new known deviation,
  or a view left out of the Anbennar gate, needs the maintainer's consent.
- **Profiles:** for every capture of a profiled window, the visibility the
  profile predicts for each path it names matches the capture's; the texts
  from `save` sources are reported against the capture's.
- **Budgets:** the gated budgets of section 9, vanilla and Anbennar; the live
  game's and pick mode's measures reported.
- **Live game:** the reload policy's rows run with Etch's own plugin in
  vanilla and in the Anbennar playset without a crash, and the live checks
  left for the plugin hold or have a recorded workaround: reopening the
  province after a restart (H8), VS Code coming forward under Windows' default
  foreground lock, real mouse and keyboard in pick mode, the hotkey with the
  province view on screen.
- **Large mods:** every window the Anbennar playset overrides opens in the
  offline renderer without a crash, with its profile applied where it has one.
- **The trial:** the maintainer edits `provinceview` in P2KE Patch - Anbennar
  and in vanilla on the candidate VSIX, through the live game (reload, pick,
  snapshot) and through the preview's views and sample data, and the run is
  recorded in `docs/` with its notes.
- **CI:** the required checks of ADR 0004 are green on `main`.
- **Release:** the README, the store README and the Etch site describe the
  live game and say how to stay on 1.0.x (ADR 0005); this specification is
  frozen and `after-v2.md` takes over.

## 15. Repository layout and conventions

As v1 section 13, with:

- `packages/core` gains the profile reader and the save reader and still never
  imports `vscode`.

  the EU4 engine lab's procedure.

## 17. Open points

Small unknowns of v2; those of the offline renderer stay in
[after-v1.md](after-v1.md#open-points).

- Reopening the province after a restart through `0x139C830` (H8 of the
  reload checks): best effort until the plugin has it; until then Etch says the
  view was not reopened (docs/live-game.md).
- The vanilla province view's reload misses its 150 ms target with the stale
  check's reads (docs/budgets.md, M8).
- The private profile keeps one `save games/` for every playset, so
  **Continue** may offer another playset's save.
- The game Exit to Main Menu starts again ran without Anvil in the M8 run, so
  the live game closes it and stops instead of adopting it.
- Real hardware input in pick mode: checked with posted messages only (in M9
  too, where `SendInput` was refused to the agent); VS Code coming forward
  under the default `ForegroundLockTimeout` and `Ctrl+Shift+E` with the
  province view on screen held in M9 (docs/pick-mode-checks.md).
- Whether `GetKeyState` alone tracks Ctrl and Shift with a real keyboard (the
  plugin also tracks them from key messages, which is what matched in M9).
- Esc in pick mode with a real key: a posted Escape closed nothing, with pick
  mode on or off.
- The time from the save in VS Code to the plugin's call (the watcher and the
  pipe): not measured yet.
- Panel rebuild leaks beyond 20 reloads of one file.
- Whether `reload assets` reloads sprite types; until it is checked a `.gfx`
  change is a planned restart.
- Starting the player's `eu4.exe` directly, without Steam, beside the live
  game (not tried, H11).
- The game date in a live snapshot needs `anvil-game.game` to offer it.
- `definition_line` in `tongs.ui` ([tongs#86](https://github.com/happy-dwarf-team/tongs/issues/86)):
  merged in Tongs and checked in M9 with a lab build; Etch pins Tongs 0.17.0,
  which has no line, until a Tongs release carrying it is pinned. Until then a
  pick finds its widget by the names of its chain (docs/live-game.md).
